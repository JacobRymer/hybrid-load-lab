# hybrid-load-lab

Comparing what a sports watch says about training load and readiness with how a hybrid/HYROX athlete's legs actually feel.

**Status: v0.1, in development.** The pipeline runs on synthetic demo data. Real-data analysis is not yet published.

## The problem

Watch-based load and readiness scores are built mainly from heart rate (for example TRIMP-style training load). They do not know how my legs were loaded: a sled push, a set of walking lunges, wall balls and an easy run can produce similar heart-rate numbers but very different leg demands. They also ignore subjective inputs such as energy, motivation and soreness. For hybrid and HYROX training, where running and strength-endurance stations are mixed in the same week, that gap matters.

## Aims

1. **Separate metabolic and leg load**, instead of one combined number.
2. **Add subjective inputs** (legs, energy, motivation, soreness, sleep) through simple daily and per-session logs.
3. **Compare what my watch says with how my legs feel**, and see where they disagree.
4. **Rule-based session guidance**: simple, transparent rules (not a black-box model) to suggest whether a planned session still makes sense.

## Methods and evidence notes

- **Daily load.** The watch-derived training load per session (intervals.icu `icu_training_load`, field name unverified), summed per calendar day, with rest days as zero. This is treated as a **mechanical load proxy** based mainly on heart rate, not a direct measure of what the muscles did. <!-- TODO: cite source for intervals.icu training load calculation -->
- **Acute:chronic (A:C) ratio.** The 7-day average load divided by the 28-day average load, using rolling averages and, as an alternative, exponentially weighted averages. It is used **descriptively**: it shows how the last week compares with the recent norm. It is not used as an injury-risk score. Values are left empty until 28 days of data exist. <!-- TODO: cite original A:C ratio work and the EWMA variant --> <!-- TODO: cite critiques of the A:C ratio -->
- **Chart bands.** 0.8–1.3 is labelled "in line with recent norm" and above 1.3 "above recent norm". These are display conventions, not thresholds with a proven meaning for an individual. <!-- TODO: cite source for the 0.8-1.3 convention -->
- **Monotony and strain.** Weekly mean load divided by its standard deviation (monotony), and weekly total load times monotony (strain). <!-- TODO: cite original monotony/strain source -->

## Limitations

- **A wrist watch cannot measure neuromuscular fatigue.** Heart-rate-based load is at best a proxy for mechanical load on the legs.
- **n = 1.** This is a single-athlete project. Nothing here generalises to other people without proper study.
- **Wrist heart rate under-reads on station work.** Optical HR is less reliable during sleds, carries and wall balls (grip, wrist flexion, short efforts), so HR-based load is likely to under-count those sessions. <!-- TODO: cite evidence on optical HR accuracy during resistance/station work -->
- The `FIELDS` mapping to intervals.icu field names is not yet verified against real data.
- Rule-based guidance will be a set of personal heuristics, not medical or coaching advice.

## How to run on demo data

Requires [Miniconda](https://docs.conda.io/en/latest/miniconda.html) (or Anaconda).

```bash
conda env create -f environment.yml
conda activate hll
python scripts/plot_acwr.py --demo
```

This writes `docs/img/acwr_demo.png` and `docs/img/acwr_demo.html`. Run the tests with `pytest` and the linter with `ruff check .`.

To use your own intervals.icu data, copy `.env.example` to `.env`, fill in your API key and athlete ID, then run `python scripts/check_connection.py` and `python scripts/sync.py`.

## Data and privacy

- **Real data stays local.** API keys live in `.env`; downloaded data goes to `data/raw/` and `data/processed/`, personal logs to `data/log/`, and real charts to `outputs/`. All of these are git-ignored, as are `.fit`, `.gpx` and `.tcx` files.
- **Only synthetic data is published.** Charts in `docs/img/` and test fixtures are generated from synthetic data.
- `check_connection.py` reports which fields exist and how many values they have; it never prints note text.
